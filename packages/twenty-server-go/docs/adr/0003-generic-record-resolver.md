# ADR 0003 — Serve runtime-built record operations from one generic resolver

The front end builds the record operations (`FindMany<Plural>`, `FindOne<Singular>`, `FindDuplicate<Singular>`, `Create…`, `Update…`, `Delete…`, `Destroy…`, `RestoreMany…`, `Merge<Plural>`, `GroupBy<Plural>`, `Aggregate<Plural>`, `<Plural>GroupByAggregates`, `<Plural>GroupByRecords`) from object metadata, so every object, including custom ones, has the same 17. A gqlgen schema per object does not scale: `generated.go` is already 3.5MB for nine objects. Instead `recordsgql.Dynamic` parses the incoming query with gqlparser, maps each root field to an operation by the object's singular and plural names, and walks the selection set against `model.Objects`, so composite fields, relations, connections, aggregates and groups are projected from the field model with no per-object code. `store.Dynamic` is the matching store: rows are column-keyed maps over the existing `table` filter, order, cursor, aggregate and group-by compiler.

Adding an object is a registration: its name in `frontdoor.RuntimeBuiltObjects` (which routes its 17 operations to Go) and, only if the front end offers duplicate detection for it, an entry in `duplicateCriteria` in `cmd/api/dynamic_records.go`. The nine objects with gqlgen schemas keep their existing `Aggregate*`, `*GroupByAggregates` and `*GroupByRecords` handlers; the generic resolver serves the other fourteen operations.

Limits, taken knowingly. The model carries no relation metadata beyond the join column, so a many-to-one target is found from the field name (`company`, `targetPerson`, a short alias table) and a one-to-many field from a `NamePlural` match plus a back-reference; any other relation answers `BAD_USER_INPUT` rather than empty data. `Merge` fills empty columns of the priority record from the others in id order, repoints many-to-one columns named after the object and soft-deletes the rest; it does not union array fields as Node does. Writes through the generic path do not publish person events, which only `store.People.WithEvents` does. Responses are not validated against a schema, so a malformed selection fails only when a row is projected.
